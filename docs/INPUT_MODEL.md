# 输入模型：一台设备一套规则

> 结论先说：**「上/下/确认/返回」是共享词汇，但产生它们的方式、重复的节奏、以及按下与松开之间的语义，三种设备没有一处相同。** 把它们塞进同一条规则，就会得到「键盘按住方向键只走一格」「手柄按一下等于按了两次」「鼠标划过卡片时高亮在后面追」这类症状。

代码位置：`lib/core/input/`

| 文件 | 职责 |
|---|---|
| `input_action.dart` | `InputAction` 词汇表 + `InputDevice` + `InputIntent` |
| `keymap.dart` | 物理键 → 动作（唯一知道键身份的地方） |
| `held_repeat.dart` | 手柄方向的重复节奏（键盘不用它） |
| `gamepad.dart` | XInput 轮询 → 动作 |
| `input_router.dart` | 单一键盘入口 + 分层栈 + 设备记录 |

---

## 1. 三种设备的规则对照

| | 键盘 | 手柄 | 指针（鼠标/触控板） |
|---|---|---|---|
| 事件形态 | 离散事件（按下/重复/抬起） | **状态**，需要轮询 | 坐标 + 按钮 |
| 重复从哪来 | **操作系统**（用户自己的重复速率） | **我们自己合成**（350/110/50ms） | 不存在 |
| 模拟量 | 无 | 左摇杆，径向死区 0.16 + 主导轴 | 无 |
| 确认方式 | 焦点树（Enter/Space） | `FocusNavigator.activate()` | 直接点中目标（`onTap`） |
| 高亮动效 | **滑行**（有惯性，是「焦点移动了」的唯一提示） | **滑行**（同上） | **瞬移**（光标已经在目标上，滑行＝迟到） |
| 断开/失焦 | 无此概念 | 掉线 ≠ 按键，只清状态 | 无此概念 |
| 原始键名 | 保留并转发给 OSD | 只能映射到动作子集 | 无 |

### 1.1 键盘不套用手柄的重复规则

Windows 会按用户设置的系统重复速率持续投递 `KeyRepeatEvent`（默认约 500ms 后每 31ms 一次）。如果我们在上面再加一层 `HeldRepeat`，按住方向键就会**一步变两步**。

所以 `InputRouter._onKey` 对 `KeyRepeatEvent` 的处理是「放行或丢弃」，从不自己计时：

```dart
if (repeat && !action.repeats) return false;   // 确认/返回永不因长按重放
return dispatch(InputIntent.action(action, device: InputDevice.keyboard, repeat: repeat, key: event));
```

`InputAction.repeats` 是唯一裁决者：导航、翻页、跳转、音量、快进快退为 `true`；`confirm`/`back`/`contextMenu`/`toggleDock` 为 `false`。按住 Enter 确认两次会跳过一个界面，这不是「更灵敏」，是 bug。

### 1.2 手柄不套用键盘的规则

手柄按住 D-pad 只产生一次按下，之后**永远沉默**——没有系统重复可用。`HeldRepeat` 复现上游 `core/held_step.hpp` 的节奏：

| 阶段 | 间隔 |
|---|---|
| 按下瞬间 | 立即一步 |
| 第一个重复之前 | 350 ms |
| 第 2–6 次 | 110 ms |
| 第 7 次起 | 50 ms |

`test/input_layer_test.dart` 锁了这段：3 秒按住应产出 40+ 步；如果节奏坏成固定 110ms，只会是 25 步左右。

摇杆则是另一件事：**没有「键」可言**。先算径向模长，低于 0.16 视为归零，再取主导轴——否则斜推 45° 会在两个方向之间抖动。D-pad 优先于摇杆，两者共用同一个 `HeldRepeat`，这样「摇杆推着推着改按 D-pad」不会被当成一次新按下而多走一格。

### 1.3 指针不套用「聚焦→确认」两步

键盘和手柄只能「移动焦点，再确认」，这是它们的物理限制。指针不是：它直接指向目标。

所以 `TvFocusable` 的指针路径是 `onEnter → requestFocus`（只为让高亮跟手）+ `onTap → onSelect`（直接执行）。点一下只发生一次动作，不经过 `activate()`。

副作用是高亮必须**瞬移**：`GlideFocusStage._report` 在设备为指针时直接 `snap`，其余设备保留弹簧滑行。这一段是有来历的——用户的原话是「鼠标操作会严重飘逸」，而现象正是高亮在 200ms 里追赶光标，眼睛先到、光圈后到。

### 1.4 指针也没有「重复」

滚轮是连续量，不是按住的键。播放页的滚轮仍按「一格」转发给 OSD（由 Lua 决定是音量 ±5% 还是菜单行），大厅不做滚动劫持——指针悬停即聚焦，滚动再去改焦点只会和光标打架。

## 2. 分层栈：谁能看到这一下

```
InputRouter (唯一的 HardwareKeyboard 处理器)
  └── 栈，后进先出
        player      ← 播放页（route）
        hub         ← 详情页（route）
        source-dialog
        shell       ← 常驻，最后才轮到
```

- 每个页面在 `initState` 订阅、`dispose` 取消。**顺序由栈决定，不再由 widget 生命周期碰运气**。以前五个文件各自 `addHandler`，谁先收到键取决于谁先初始化，`Esc` 因此要在大厅、控制中心、播放页各写一遍。
- 播放页只认领自己需要的：键盘事件带原始 `KeyEvent`（OSD 的键表比动作表大得多：`[`、`]`、数字、`alt+n`），手柄走 `OsdKeys.nameForAction` 的动作子集。**把键映射成动作再映射回去会丢掉大半键位**，所以没有这么做。
- 大厅的浮层退栈是 `_overlays` 列表（dock → panel → search），`Back` 永远只弹一层。新加浮层只需在列表里加一行，不用再教一遍 `Esc` 阶梯。

### 2.1 文本输入优先

`TextEntry.active` 为真时，路由只放行 `back`，其余键全部交还给输入框（包括它依赖的重复事件）。这个判断通过 `InputRouter.textEntryActive` 回调注入，`core/` 不反向依赖 `ui/`。

## 3. 做了什么，没做什么

**已实现**

- `InputAction` 25 个动作，`Keymap` 表驱动，`OsdKeys.nameForAction` 供手柄使用。
- 分层栈 + 指针/键盘/手柄三套设备规则 + 高亮瞬移。
- XInput 轮询（`xinput1_4.dll`，结构体 16 字节，启动时用 `sizeOf` 校验，不符就整体放弃而不是越界写内存）。
- `test/input_layer_test.dart`：重复节奏、设备语义、键表边界。

**未实现 / 未验证**

- 手柄的**设置项**（`swapConfirm` 是常量，没进 `prefs`）、死区可调、震动。
- 手柄热插拔的 UI 反馈（掉线只清状态，不弹提示）。
- 真实手柄从没在这台机器上接通过：`XInputGetState` 四个槽位全部返回 1167（未连接），所以「按下 A 会不会激活焦点」只有静态推理，没有实测。
- 斜推摇杆在主导轴切换点可能抖动，上游同样没有加滞回，暂未处理。
- 键盘方向键是否真的到达了 `InputRouter` 而没有被 `WidgetsApp` 的默认方向遍历先吃掉——旧代码在这个位置就是全局处理器，语义未变，但**这一点只在本机出包后按方向键才能确认**。
